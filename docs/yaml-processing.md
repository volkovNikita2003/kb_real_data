# Обработка YAML и проверка данных

## Назначение рефакторинга

Ранее `parameters.py` и `calibration/refactoring/result.py` независимо
реализовывали безопасный YAML loader, отклонение повторяющихся ключей,
проверку полей и чисел, преобразование dataclass и запись YAML. Такие копии
могли со временем начать по-разному обрабатывать `bool`, `NaN`, неизвестные
поля или ошибки файловой системы. Добавление формата результата DARL привело
бы к появлению третьей реализации.

После рефакторинга обработка разделена на три уровня:

```text
yaml_support.py
    чтение и запись формата YAML
              ↓
schema_validation.py
    проверка декодированных значений и структуры одной схемы
              ↓
parameters.py / */result.py
    конкретные модели, поля, значения по умолчанию и предметные правила

validation.py
    проверка каталогов, файлов и связей всего эксперимента
```

Каждый уровень решает только свою задачу. Вычислительный код калибровки этим
рефакторингом не изменялся.

## `yaml_support.py`

Модуль содержит единственное в производственном коде прямое использование
PyYAML. Он ничего не знает о камере, калибровке, DARL или восстановлении.

### `load_yaml()`

```python
value = load_yaml(path)
```

Функция:

- читает UTF-8;
- использует безопасный loader PyYAML;
- запрещает Python-теги и создание произвольных объектов;
- отклоняет повторяющиеся ключи на любом уровне;
- отклоняет пустой документ;
- различает отсутствующий файл и каталог вместо файла;
- преобразует технические ошибки в `YamlError`.

Функция возвращает декодированное значение без проверки конкретной схемы.
Корнем документа может быть mapping, список или скаляр. Требование корневого
mapping задаёт уже предметный загрузчик.

### `dump_yaml()`

```python
dump_yaml(path, value)
dump_yaml(path, value, overwrite=False)
dump_yaml(path, value, create_parents=False)
```

Функция использует `yaml.safe_dump`, UTF-8, сохраняет порядок полей и
поддерживает Unicode. Сначала данные полностью сериализуются в памяти, и
только затем открывается целевой файл. Поэтому неподдерживаемое значение не
обнуляет уже существующий файл.

`overwrite=False` используется для `used-parameters.yaml`: повторная запись
такого файла считается ошибкой. Архивированием целых каталогов управляет
`output.py`, а не YAML-модуль.

### `to_plain_data()`

Функция рекурсивно преобразует объекты проекта в структуры, допустимые для
безопасной записи YAML:

- dataclass — в mapping;
- `Mapping` — в обычный `dict` со строковыми ключами;
- список и кортеж — в список;
- `Path` — в строку.

Обычное значение `None` сохраняется как YAML `null`. Это важно, например,
для `class_slice.drop_last`.

Иногда `None` означает не значение поля, а отсутствие целой секции. Такие
поля явно помечаются в dataclass:

```python
camera: CameraParameters | None = field(
    default=None,
    metadata={YAML_OMIT_NONE: True},
)
```

Только помеченное поле пропускается при сериализации. Благодаря этому
отсутствующая линейка не записывается как `line_sensor: null`, но значимые
`null` в других частях схемы сохраняются.

### `YamlError`

`YamlError` является низкоуровневой ошибкой формата или файла. На границе
предметного модуля она преобразуется в соответствующую ошибку:

```python
try:
    value = load_yaml(path)
except YamlError as error:
    raise ParametersError(str(error)) from error
```

Для результата калибровки используется `CalibrationResultError`, а для
будущего результата DARL будет использоваться `DarlResultError`.

## `schema_validation.py`

YAML loader отвечает только за синтаксис. Например, он корректно прочитает
`width_px: true`, хотя для параметра ширины это недопустимо. Проверку
декодированных значений выполняет `SchemaValidator`.

Валидатор создаётся с типом предметного исключения:

```python
PARAMETERS_VALIDATOR = SchemaValidator(ParametersError)
CALIBRATION_VALIDATOR = SchemaValidator(CalibrationResultError)
```

Он предоставляет единые примитивы:

- `mapping()` — mapping со строковыми ключами;
- `fields()` — обязательные, необязательные и неизвестные поля;
- `string()` — строка и правило пустого значения;
- `boolean()` — строго `bool`;
- `integer()` — строго `int`, без принятия `bool`;
- `number()` — `int` или `float`, но не `bool`, `NaN` и бесконечности;
- `choice()` — значение из заданного набора;
- `version()` — точное соответствие поддерживаемой версии схемы.

Ограничения `positive` и `non_negative` применяются одинаково во всех
параметрах и результатах.

`SchemaValidator` не читает файлы и не импортирует модели проекта. Он получает
уже декодированные Python-значения. Ошибки в самих данных создаются с заданным
предметным типом исключения. Противоречивое описание схемы, например, одно поле
одновременно в `required` и `optional`, считается ошибкой разработчика.

## Предметные модули

`parameters.py` определяет:

- поддерживаемые секции входных файлов;
- обязательные и необязательные поля;
- значения по умолчанию;
- согласованность наборов детекторов;
- фактически использованные параметры этапов.

Он использует `load_yaml()` и `SchemaValidator`, но сохраняет предметную
обёртку `_load_yaml()`: она требует mapping в корне файла и преобразует
`YamlError` в `ParametersError`. Это не дублирование YAML loader.

`calibration/refactoring/result.py` определяет структуру результата
калибровки, набор его полей и правила вроде
`start_angle_deg < end_angle_deg`. Чтение, запись и стандартные проверки
переданы общим модулям. Метод `CalibrationResult.to_dict()` остаётся
предметным интерфейсом: он решает, какие секции входят в результат.

Будущие `darl/result.py` и `restore/result.py` должны использовать те же
общие функции, не создавая собственные YAML loader и проверки чисел.

## Почему разделены `schema_validation.py` и `validation.py`

Несмотря на похожие названия, модули проверяют разные уровни системы.

| Модуль | Что проверяет | Чего не знает |
|---|---|---|
| `schema_validation.py` | Одно декодированное значение или mapping | Каталоги эксперимента, измерения, экспозиции и фон |
| `validation.py` | Файлы, каталоги и согласованность эксперимента | Внутреннюю реализацию YAML loader и стандартных проверок типов |

Пример обработки `general.yaml`:

1. `yaml_support.load_yaml()` читает документ и отклоняет повторяющиеся ключи.
2. `SchemaValidator` проверяет, что `width_px` — положительное целое число.
3. `parameters.py` создаёт `GeneralParameters` и применяет значения по
   умолчанию.
4. `validation.py` проверяет, что данные включённого детектора действительно
   присутствуют в структуре эксперимента.

`validation.py` также проверяет:

- наличие обязательных директорий детекторов;
- допустимость файлов внутри них;
- формат и соответствие экспозиций;
- сигнал и фон камеры и линейки;
- существование измерений и профилей восстановления;
- соответствие файлов ожидаемых распределений реальным измерениям;
- предупреждения о данных отключённых детекторов.

Объединение этих модулей связало бы универсальную проверку типов с конкретной
структурой эксперимента и затруднило повторное использование схем в
результатах калибровки, DARL и восстановления.

## Добавление нового YAML-формата

Для нового файла параметров или результата следует:

1. Описать предметные dataclass-модели.
2. Прочитать документ через `load_yaml()`.
3. Проверить поля и типы через `SchemaValidator` с предметным исключением.
4. Добавить только специфические правила, которых нет в общем валидаторе.
5. Сохранять через `dump_yaml()`.
6. Использовать `YAML_OMIT_NONE` только когда `None` означает отсутствие
   секции, а не значение `null`.
7. Добавить тесты схемы и интеграционный тест чтения и записи.

Прямой импорт PyYAML за пределами `yaml_support.py` в производственном коде
не допускается.

## Тестирование

`tests/test_yaml_support.py` проверяет безопасное чтение и запись, Unicode,
повторяющиеся ключи, запрещённые Python-теги, пустые документы, защиту от
перезаписи и правила `YAML_OMIT_NONE`.

`tests/test_schema_validation.py` проверяет строгие типы, отличие `bool` от
чисел, `NaN`, бесконечности, ограничения значений, поля и версии схем.

Предметные тесты параметров и результата калибровки подтверждают, что общие
утилиты правильно встроены в публичные загрузчики.
